## Phase 2 — Database, Migrations, Models & Relationships (complete)

- **Migrations** (in dependency order): `create_companies_table`, `add_role_and_company_id_to_users_table`, `create_subscriptions_table`, `create_transactions_table`, `create_audit_logs_table`.
- **companies**: administrative `status` (active/inactive) only — never a payment state. `ntn_cnic`/`email` unique. `SoftDeletes` so historical financial records outlive a deleted company.
- **users**: added `role` (admin/company) and nullable `company_id` FK (admin ⇒ null, company ⇒ owning company; PRD #29). `restrictOnDelete` — a company with users can't be hard-deleted.
- **subscriptions**: `type` (monthly/yearly), `status` (active/pending/expired/cancelled), `starts_at`/`ends_at` (datetime, for precise expiry comparisons), `amount`. `restrictOnDelete` on `company_id`.
- **transactions**: full field set from PRD #24, plus a generated `pending_dedupe_key` column (`NULL` unless `status = 'pending'`, else `= subscription_id`) with a unique index on it — the database itself now rejects a second pending transaction on the same subscription (PRD #50/#51), on top of the app-level check that later phases will still perform. Verified this works identically on MySQL (`SHOW CREATE TABLE`) and SQLite (test suite).
- **audit_logs**: `user_id`/`company_id` nullable with `nullOnDelete` — deliberately different from the financial tables' `restrictOnDelete`, since an audit row must survive the account it references, not block that account's removal.
- **companies**: FBR production and sandbox tokens are stored on the company record and redacted from audit values.
- **Models**: `Company`, `Subscription`, `Transaction`, `AuditLog`,  created; `User` extended with `role`/`company_id`, a `company()` relation, and `isAdmin()`/`isCompany()` helpers. Used this codebase's existing `#[Fillable]`/`#[Hidden]` attribute style (matching the pre-existing `User` model) rather than mixing in classic `protected $fillable` properties.
- **Relationships**: exactly as specified in PRD #34 (`Company` ⇒ hasMany Users/Subscriptions/Transactions; `Subscription` belongsTo Company, hasMany Transactions; `Transaction` belongsTo Company/Subscription; `User` belongsTo Company), plus `Company::latestSubscription()` (hasOne, latestOfMany — a data-access convenience only; "current/active for access control" business logic is deliberately left for Phase 5/7).
- **Factories**: added for all five new models, with `Company::factory()->inactive()`, `Subscription::factory()->monthly()/yearly()/pending()/expired()/cancelled()`, `Transaction::factory()->pending()/cancelled()/renewal()/yearly()`. `UserFactory` now defaults to a valid admin (`role=admin`, `company_id=null`) and gained `->admin()`/`->company($company)` states.
- **Seeder**: `DatabaseSeeder` now seeds one local-dev admin (`admin@invoxpakistan.test`) via `User::factory()->admin()`; company/subscription/transaction seeding deferred until their creation flow exists (Phase 4+).
- **Tests**: 6 new Feature test classes under `tests/Feature/Models/` (Company, Subscription, Transaction, AuditLog, , User) — 21 new tests / 44 new assertions, covering relationships, soft deletes, uniqueness constraints, the pending-transaction dedupe constraint, encrypted-at-rest FBR credentials, and hidden-attribute serialization. Full suite: 24/24 passing.
- **Verification**: ran migrations on the real MySQL dev database (not just SQLite test DB), inspected the generated `pending_dedupe_key` column via `SHOW CREATE TABLE`, rolled every migration back and forward again to confirm `down()` methods are correct, ran `php artisan model:show Company` to confirm schema/relations wiring, and `vendor/bin/pint --test` for code style.
- **Decision — no DB-level CHECK constraint** for "admin ⇒ company_id null / company ⇒ company_id set": SQLite (used by the test suite) can't add a `CHECK` constraint via `ALTER TABLE` to an existing table, only at creation time, which would make the constraint fragile across the two drivers this project runs on. This invariant is enforced at the application layer instead (`UserFactory` states now, model/Form Request validation in Phase 3+).
- **Decision — `transaction_type` enum values** (`initial`/`renewal`): the PRD names the column but doesn't enumerate its values; these two map directly to the flows in PRD #24-#27 (first invoice vs. every subsequent renewal invoice).

## Phase 3 — Authentication & Authorization (complete)

- **Single `users` table, single `web` guard** — no separate guards/providers for admin vs. company. "Separate logical areas" (PRD #5) is achieved with two login routes/controllers/views plus role-checking middleware, not two auth systems, since Phase 2 already modeled admin/company as one `users` table with a `role` discriminator.
- **Middleware**: `EnsureUserIsAdmin` (alias `admin`) and `EnsureUserIsCompany` (alias `company`) — registered in `bootstrap/app.php`. Each just checks `$request->user()->isAdmin()/isCompany()` and aborts 403 otherwise; this is a pure role gate, not a subscription check (that's `CheckCompanySubscription` in Phase 7).
- **Guest/auth redirects**: since there's no single `/login` route, `redirectGuestsTo` sends an unauthenticated visitor to whichever portal's URL they hit (`/admin/*` → admin login, else company login); `redirectUsersTo` sends an already-authenticated user hitting a login page to their own dashboard based on their actual role — an admin can never be bounced into the company login flow or vice versa.
- **Login is role-scoped at the credential-check level, not just after**: `AdminLoginRequest`/`CompanyLoginRequest` pass `role => 'admin'`/`role => 'company'` straight into `Auth::attempt()`, so a company account's correct password fails the admin form exactly like a wrong password would (PRD #4.2) — the failure message never reveals whether the email, password, or role was wrong. Modeled on Laravel's standard Breeze `LoginRequest` pattern (per-IP+email rate limiting via `RateLimiter`, 5 attempts) — no new package added, just the well-known idiom, kept in a Form Request per the PRD's Form Request requirement.
- **Routes**: `routes/admin.php` and `routes/company.php` (required from `web.php`, Breeze-style) — `admin/login`, `admin/logout`, `admin/dashboard`; `company/login`, `company/logout`, `company/dashboard`. `company/subscription-required` is intentionally not added yet — it belongs to Phase 7 alongside the middleware that redirects to it.
- **Controllers**: `Auth\AdminLoginController`, `Auth\CompanyLoginController` (create/store/destroy); `Admin\DashboardController`, `Company\DashboardController` — both dashboards are placeholder pages for now ("login + role gate work"), with the real content explicitly deferred to Phase 8 (admin) and Phase 5/7 (company subscription info).
- **Views**: `layouts/auth.blade.php` (centered card, used by both login forms), `layouts/admin.blade.php` (navbar + sidebar with **Dashboard / Companies / Audit Logs** per PRD #12 — Companies/Audit Logs render as disabled "soon" placeholders since their routes don't exist until Phase 4/10, rather than linking to routes that don't exist yet), `layouts/company.blade.php` (navbar only, no sidebar), `auth/admin-login.blade.php`, `auth/company-login.blade.php`, `admin/dashboard.blade.php`, `company/dashboard.blade.php`. Added Admin/Company login buttons to the Phase-1 homepage so the whole flow is reachable by hand.
- **Tests**: `tests/Feature/Auth/AdminAuthenticationTest`, `CompanyAuthenticationTest`, `RoleAccessTest` — 20 new tests covering: successful login+redirect, wrong password, cross-role login rejection (company creds on admin form and vice versa), logout, guest redirect to the correct login page, already-authenticated redirect away from login, rate limiting after 5 failed attempts, and — the PRD #62 Phase 3 acceptance criteria — an authenticated admin gets 403 on every company route and an authenticated company user gets 403 on every admin route. Full suite: 44/44 passing.
- **Manual verification**: booted the app, logged in as the seeded admin and a manually-created company user through the real browser UI, confirmed dashboards render, confirmed cross-role login rejection shows the generic Laravel error, confirmed logout returns to the correct login page, confirmed 403 when an authenticated user of one role requests the other role's dashboard by URL. Reset the dev DB back to just the seed afterwards.
- **Decision — CSRF in tests**: relied on Laravel's built-in `runningUnitTests()` bypass in `PreventRequestForgery` rather than disabling CSRF middleware manually; confirmed this before writing tests so the passing suite reflects real route/controller behavior, not weakened middleware.

## Phase 5 — Subscription System (complete)

- **No new migrations** — Phase 2 already has everything (`type`, `status`, `starts_at`, `ends_at`, `amount`); this phase is entirely behavior on top of that schema.
- **`Subscription` model gained the status/access-rule helpers** the rest of the app now depends on:
  - `isActive()` — the literal PRD #10 Company Access Rule: `status === 'active'` **and** `ends_at` hasn't lapsed. Checks both deliberately — a stored `status` of "active" whose `ends_at` has already passed (because Phase 11's scheduler hasn't run yet) must NOT count as active, and this is the method Phase 7's middleware will call directly rather than re-deriving the rule itself.
  - `hasLapsed()` — pure date check (`ends_at` in the past), independent of the stored `status`, i.e. "reality" vs. "what the DB currently says."
  - `isPending()`, `isExpired()`, `isCancelled()` — raw status checks.
  - `daysRemaining()` — whole days to `ends_at`, floored at 0 once passed (PRD #47).
- **`Domain\Subscriptions\SubscriptionRenewal::renew($subscription, $paymentDate = null)`** — PRD #27's two-branch renewal math, built and tested now even though nothing calls it yet in a route (Phase 6's "mark transaction paid" flow will be the first caller, alongside its own Transaction/AuditLog writes, similar to how Phase 4's `CompanyOnboardingService` composes `SubscriptionPeriod`):
  - Payment arrives at or before the current `ends_at` → new period starts the day **after** the current `ends_at` (never shortens unused time). Verified against the PRD's own worked example (20-Aug end, 10-Aug payment → 21-Aug start, 20-Sep end) and the exact boundary (`ends_at` and payment date on the same instant → still extends, doesn't restart — consistent with #10's "≥").
  - Payment arrives after `ends_at` has already lapsed → new period starts on the payment date itself.
  - Always sets `status` back to `active` on success, regardless of what it was before (pending/expired) — renewal is unconditional once called; the *decision* to call it (e.g. only for a genuinely pending transaction) belongs to Phase 6.
- **Company dashboard now shows real data** (fulfilling the placeholder note left in Phase 3): subscription type/status/start/end/days-remaining (PRD #47), an expiry warning banner inside 7 days (PRD #48 — the PRD's own example uses 3 days but doesn't mandate a threshold; 7 was chosen and documented here since it wasn't specified), and — reusing PRD #10's exact wording — a blocking-style message when the subscription isn't currently active, whether that's because it's genuinely `pending`/`expired` or because the stored `status` is stale and `hasLapsed()` catches it first. The warning is purely informational: nothing here blocks access yet, since the `subscription` middleware is still Phase 7. Company data comes only from the authenticated user's own `company()` relation — no ID is ever read from the request (PRD #41).
- **Tests**: `SubscriptionRenewalTest` (5 tests covering the PRD's before/after/exact-boundary/yearly/default-to-now cases), new assertions in `Feature\Models\SubscriptionTest` for all the status helpers including the "stale status" scenario, and `Feature\Company\DashboardTest` (6 tests: healthy, expiring-soon, not-yet-expiring, pending, stale-active-but-lapsed, and no-subscription-yet). Full suite: **93/93 passing**.
- **Manual verification**: on the real MySQL dev DB, created three companies via `CompanyOnboardingService` (healthy / 2-days-from-expiry / lapsed-but-still-marked-active), logged into each through the real browser and confirmed the dashboard showed the right message and day count for each, then called `SubscriptionRenewal::renew()` live via tinker against the lapsed one and confirmed both the DB row and the already-open dashboard page reflected the new period on refresh.

- **`Domain\Transactions\MarkTransactionAsPaid::handle($transaction, $notes = null)`** — the atomic "Mark Pending Transaction as Paid" flow (PRD #26/#53): re-fetches the transaction under `lockForUpdate()` (guards a genuine concurrent-request race, not just a same-tab double-click), verifies it's still `pending`, sets `status=paid`/`paid_at=now()`, calls Phase 5's `SubscriptionRenewal::renew()`, all inside one `DB::transaction()`. - **Controller/route**: `Admin\TransactionController::markPaid`, `POST /admin/transactions/{transaction}/mark-paid` — a top-level route (not nested under companies), matching PRD #38 exactly. Full suite: **115/115 passing**.

- **Tests**: `Admin\DashboardTest` (7 tests) — access control (admin ok, guest redirected, company user 403), the summary-card counts specifically proven against a mix of active/pending/stale-active-but-lapsed/no-subscription companies (so the "real-time, not stored-status" behavior is actually exercised, not just assumed), companies overview content, and recent-payments filtering + ordering. ## Phase 9 — Pending Companies (complete)

## Phase 11 — Subscription Scheduler (complete)

- **`Subscription::scopeNeedingExpiryProcessing()`** — PRD #49's starting query, "Find active subscriptions -> Check ends_at" (`status = 'active' AND ends_at < now()`). Deliberately status-based rather than the inverse of `currentlyActive()`: a subscription already reconciled to pending/expired/cancelled (by a previous run, or manually) is left alone rather than reprocessed — verified directly with a test seeding a `cancelled` subscription past its end date and confirming the command doesn't touch it.
- **`Console\Commands\ProcessExpiredSubscriptions`** (`php artisan subscriptions:process-expired`): for each lapsed-but-still-`active` subscription, flips it to `pending`, writes a `subscription.expired` audit log entry (system action — `AuditLogger`'s `user_id: null` support, built in Phase 10, was exactly for this), and — only if one doesn't already exist (PRD #50) — creates its renewal invoice: `due_at` = the subscription's *old* `ends_at` (when payment actually became due, not whenever this command happened to run), `billing_period_start` = that date + 1 day, `billing_period_end` computed via Phase 4's `SubscriptionPeriod::endDateFor()` (so monthly/yearly renewal invoices use the exact same date math as initial creation).
- **Layered protection against PRD #64 case 7 ("scheduler runs twice")**: each subscription is processed inside its own `DB::transaction()` with a `lockForUpdate()` re-fetch and re-check immediately before acting — so a subscription already flipped to `pending` by an earlier iteration (or an earlier run) simply won't match `needingExpiryProcessing()`'s query on the next pass, and even if it somehow did, the pending-invoice-exists check catches it. The scheduler registration itself (`routes/console.php`) also adds `withoutOverlapping()` as a first line of defense against two runs racing at the orchestration level. Verified directly: ran the actual command twice in a row (in tests, and manually against the real dev DB) and confirmed exactly one transaction and exactly one audit log entry either way.
- **Scheduled hourly** (`Schedule::command(...)->hourly()->withoutOverlapping()` in `routes/console.php`) — the PRD says only "periodically"; hourly keeps the dashboard and Pending Companies page reasonably fresh without being excessive. Documented explicitly that **access control never depends on this timing** — Phase 7's middleware already checks `status` + `ends_at` in real time regardless of whether this command has run yet, so this scheduler's job is purely to keep the stored `status` column and the pending-invoice trail accurate for admin-facing display, not to gate anything.
- **Closes the gap Phase 9 documented and left open on purpose**: back in Phase 9, a lapsed company could sit on the Pending Companies page with no invoice to show (Invoice: "—", no Mark-as-Paid button) because nothing yet created one automatically. Verified end-to-end on the real dev DB that this is exactly what's fixed now: a manually-lapsed subscription, after one run of this command, shows up on the Pending Companies page with a real invoice number, amount, and due date, and a working Mark-as-Paid button — no code changes needed in Phase 9's views or controller at all.
- **Tests**: `Console\ProcessExpiredSubscriptionsTest` (8 tests) — monthly and yearly renewal invoice date math, still-active subscriptions left untouched, already-pending/cancelled subscriptions left alone, the double-run case, the "pending invoice already exists" case, and the system audit log entry (`user_id` null). Full suite: **158/158 passing**.
- **Manual verification**: on the real MySQL dev DB, seeded a company with a subscription lapsed 4 days ago (still stored as `active`), confirmed `php artisan schedule:list` shows the command registered hourly, ran it once and saw the correct summary output, ran it again immediately and confirmed a "0 found" no-op, then inspected the DB directly (subscription now `pending`, one new `renewal`/`pending` transaction with the right dates) and confirmed both the live Pending Companies page and the live Audit Logs page (including the full old/new status diff) reflected it correctly.

## Phase 6 — Bulk Upload (complete)

- **Format decided without new PRD text to consult (no `/docs` PRD file exists on disk this session — see the standing constraint at the top of this Company Dashboard section)**: one CSV row = one invoice item line; several rows sharing the same `invoice_reference_no` are combined into a single multi-item invoice. ### Finding and fix

- **Bulk upload had no cap on data-row count** (real gap, fixed): every row in an uploaded file is validated individually and every surviving invoice group is created inside its own `DB::transaction()` — all synchronous, within one request, with no queue/background-job mechanism anywhere in this app to fall back on. ## FBR Digital Invoicing API Integration (real Sandbox HTTP calls, replacing the stub)

Connects the invoice lifecycle built in Phases 4/6 to FBR's actual Sandbox API, per `InvoxPakistan_Invoice_FBR_Integration_Prompt.md` and `API Doc.pdf` ("Technical Specification for DI API", v1.12) — read in full before writing any code, per that prompt's own first instruction. `StubFbrInvoiceSubmitter` (Phase 4's placeholder, documented from the start as temporary "until real IRIS endpoint/credentials/payload docs are available") is now replaced with a real implementation; nothing about the surrounding lifecycle (draft → submitted → successful/failed, edit/resubmit rules, company isolation) needed to change, because Phase 4 was already built around a swappable `FbrInvoiceSubmitter` interface for exactly this moment.

### API integration details

- **Endpoint used**: `postinvoicedata_sb` (`https://gw.fbr.gov.pk/di_data/v1/di/postinvoicedata_sb`, API Doc.pdf Section 4.1) — the actual submission endpoint, not `validateinvoicedata_sb` (Section 4.2), because only the Post endpoint issues a real FBR invoice number; a "Submit Invoice" action needs one.
- **Authentication**: `Authorization: Bearer <token>` header (Section 3.1), token = `::where('company_id', $invoice->company_id)->value('fbr_token_sandbox')` — resolved fresh from the invoice's own company on every submission, never cached, never from a global/env value, never logged.
- **Company credential lookup**: entirely inside `SandboxFbrInvoiceSubmitter` (not the controller — a stray, unused `$fbr_token` fetch left in `InvoiceController::store()` from earlier work-in-progress was removed as dead code once the real lookup had a proper home). Verified live with two companies, each submitting with its own distinct token and neither ever seeing the other's (`InvoiceFlowTest::test_each_company_uses_its_own_fbr_sandbox_token`).
- **FBR payload mapping** (`FbrInvoicePayloadBuilder`): every JSON field name transcribed directly from Section 4.1.1/4.1.2's sample payloads and field tables, not guessed from local column names (they mostly, but not always, match — e.g. local `total_sales_value` → FBR `totalValues`). Seller fields come from the authenticated company's own profile (`ntn_cnic`/`business_name`/`province`/`address`); buyer fields from the invoice's own snapshot, exactly as already stored. `rate` is reformatted from this app's plain decimal into FBR's percentage string (`"18%"`, trimming trailing zeros to match the doc's own sample values exactly).
- **Scenario resolution** (`FbrScenarioResolver`): `scenarioId` (Section 4.1's field table: "Required for Sandbox only") resolved from each item's Sale Type via a lookup table transcribed directly from Section 9 ("Scenarios for Sandbox Testing") — `"Goods at standard rate (default)"` resolves to SN001/SN002 depending on buyer registration type, matching Section 9 exactly; a Sale Type with no row in Section 9 (see Known Gap below) resolves to `null` rather than a guessed value, which the submitter treats as a hard failure before ever calling FBR. Since FBR's payload carries exactly one `scenarioId` per invoice, an invoice whose items resolve to *different* scenarios is also rejected locally (`scenarioConflict`) rather than arbitrarily picking one.
- **Known gap, flagged not silently guessed**: `SaleTypeSeeder`'s `"SIM"` entry has no corresponding row anywhere in Section 9's table — the closest documented scenario (SN015, "Sale of mobile phones" / Sale Type `"Mobile Phones"`) is not the same thing as a SIM card. Left unmapped on purpose (`FbrScenarioResolverTest::test_an_unmapped_sale_type_resolves_to_null`); needs either a corrected Sale Type or FBR's actual scenario for SIM sales — a business decision, not something to guess in code.
- **FBR response storage**: `Invoice::$fbr_response` stores the full raw response — successful FBR JSON, a rejected-but-parseable FBR JSON (even from a non-200 HTTP status — see below), or a plain local message when the request never reached FBR at all (missing token, incomplete seller profile, unmapped scenario). `FbrResponseMessage::extract()` is the one place that knows how to turn either shape into a human-readable line, used both for the flash message shown to the user and available for future admin-facing tooling.
- **Invoice status lifecycle**: unchanged from Phase 4 (`SubmitInvoiceToFbr` already handled the draft → submitted → successful/failed transition, locking, and audit logging correctly) — this integration only had to supply a real `FbrInvoiceSubmitter`, not touch that orchestration.
- **QR code generation** (`FbrQrCodeGenerator`, `bacon/bacon-qr-code`, SVG output — no GD/Imagick dependency): checked every sample response in Sections 4.1.3–4.2.4 directly, and **no QR-specific payload (URL/string/token/value) is ever actually returned by this API version** — Section 6 only shows a static "print this logo + QR" compliance graphic, not a per-invoice API field. Rather than inventing a value, the QR encodes the one thing FBR *does* return that identifies the invoice: `invoiceNumber`. Documented explicitly in the class itself as a considered decision, not a confirmed answer — if FBR's real DI QR spec turns out to encode something else, only this one class needs to change. Stored as inline SVG in a new `invoices.qr_code` column, rendered directly on the new Invoice Details page.
- **Error handling**: missing Sandbox token, an incomplete seller company profile, and an unmapped/conflicting scenario are all caught locally *before* any HTTP call (`Http::assertNothingSent()` in tests) and produce clear, specific messages. `ConnectionException` (timeout/DNS/network failure) is caught explicitly. HTTP-level failures (401/500/anything non-2xx, Section 4.1.6) are **not** given their own hard-coded message — confirmed live against the real Sandbox (see below) that a 401 comes back with the exact same `validationResponse.error` shape as a normal rejection, so the real FBR-worded reason is extracted the same way regardless of HTTP status; a synthesized fallback only fires when there's truly no parseable body to read a reason from. No token or credential is ever included in any log, audit entry, or response shown to the user.
- **Draft/resubmission behavior**: unchanged — Save as Draft still never calls FBR (Phase 4's `afterSave()` already gated this correctly); a draft or failed invoice is still editable and resubmittable (`InvoicePolicy`, unchanged); a successful/submitted invoice is still locked.

### Real bugs found (not merely hypothesized — caught via linting, unit tests, and a genuine live Sandbox call)

1. **A `//` comment containing a literal `?>` silently truncated a whole PHP file.** `FbrQrCodeGenerator.php`'s first draft had a comment mentioning `` `<?xml ...?>` `` — PHP's lexer treats `?>` inside a `//` line comment as the real closing tag, ending PHP mode mid-file and swallowing everything after it (including the class's closing braces) as literal text. `php -l` caught it immediately as "Unclosed brace" at a misleading line number; bisected by bit precisely to find the actual cause. Fixed by rewording the comment to never write that exact two-character sequence together, and splitting the regex's own `?>` across a string concatenation as a second line of defense.
2. **`SplFileObject`'s `foreach` re-reading the header row** — this was Phase 6's bug (documented in that phase's own changelog entry), not a new one, but is the reason `BulkInvoiceCsvParser` was written the safer way from the start rather than being re-discovered here.
3. **A failed submission's redirect target never actually showed the failed invoice.** `attemptSubmit()`'s failure branch redirected to `company.invoices.drafts` — but `InvoiceController::drafts()` only ever queries `status = 'draft'`, so a `failed` invoice (which is what a rejected submission actually becomes) never appears there. The user landed on a page reading "No draft invoices," which read as if the invoice had vanished, even though it was correctly saved and visible on the main Invoice Listing all along. Found by manually submitting a real invoice against the live FBR Sandbox and watching where the redirect actually landed — not by reading the code, and not caught by the existing test suite either (those tests asserted the redirect *route*, not what that page actually *renders*). Fixed by redirecting a failed submission to the invoice's own new Details page instead — which always reflects whatever the invoice's current status actually is, and already has the FBR error, Edit, and Retry Submission actions right there. Two existing tests that asserted the old (broken) redirect target were updated; a new test locks in the real 401-with-real-FBR-error-body case that exposed this.
